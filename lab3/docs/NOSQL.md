# Нереляційна база для сирих даних

Окрім MySQL, кожне вимірювання зберігається в **первинному вигляді** в DynamoDB (`terraform/dynamodb.tf`):

| Параметр | Значення |
|---|---|
| Таблиця | `iot-lab3-raw-measurements` |
| Ключ розділу (partition key) | `sensor_id` (рядок) |
| Ключ сортування (sort key) | `measured_at` (рядок ISO 8601 UTC з мілісекундами, `2026-11-21T18:00:00.123Z`) |
| Режим оплати | `PAY_PER_REQUEST` |
| Інші атрибути | `message_id`, `sensor_type`, `value`, `unit`, `lat`, `lon`, `received_at`, `object_key` (камера) |

Рядки в такому форматі сортуються лексикографічно так само, як за часом, тому ключ сортування працює як діапазон часу. Запис виконує той самий `processor`, що й запис у MySQL (`functions/processor/handler.py`, `_store_raw`).

## Запит історії з нереляційної бази

Той самий ендпоінт із параметром `source=nosql`:

```bash
curl -s -H "x-api-key: $API_KEY" \
  "$API_URL/sensors/temp-01/history?source=nosql&from=2026-11-21T18:00:00Z&to=2026-11-21T18:10:00Z&limit=5"
```

Відповідь: масив у зворотному хронологічному порядку з сирими полями (без нормалізованого значення, `delta` і ознаки аномалії, їх обчислює обробник лише для MySQL).

## Порівняння двох підходів для цієї задачі

### Як виглядає запит історії

**MySQL:**

```sql
SELECT ... FROM measurements
WHERE sensor_id = 'temp-01' AND measured_at BETWEEN '2026-11-21 18:00:00' AND '2026-11-21 18:10:00'
ORDER BY measured_at DESC LIMIT 5
```

**DynamoDB** (`Query`):

```python
table.query(
    KeyConditionExpression=Key("sensor_id").eq("temp-01")
                          & Key("measured_at").between("2026-11-21T18:00:00.000Z", "2026-11-21T18:10:00.000Z"),
    ScanIndexForward=False,   # від найновіших
    Limit=5,
)
```

Обидва запити читають один діапазон за ключем; різниця в тому, що SQL оптимізатор сам вибирає індекс, а в DynamoDB шлях доступу визначений ключем таблиці.

### Які запити зручні й які ні

| Запит | MySQL | DynamoDB |
|---|---|---|
| Історія датчика за час (наш основний) | зручно, індекс `(sensor_id, measured_at)` | зручно і найдешевше: це і є схема ключа |
| Статистика по всіх датчиках (`COUNT`, `AVG`, `GROUP BY`) | зручно, один запит | неможливо без `Scan` усієї таблиці (дорого й повільно) або окремої агрегації |
| Усі аномалії за добу, незалежно від датчика | зручно (індекс на `is_anomaly, measured_at`) | потрібен окремий індекс (GSI) або `Scan`; тут і поля аномалії немає |
| Пошук за довільним полем (значення > X) | зручно | дорого: `Scan` з фільтром читає й оплачує всю таблицю |
| Зв'язки між таблицями, `JOIN` | є | немає |
| Транзакції з кількох таблиць | є | обмежені |
| Запис «ключ-значення» з високою частотою | можливий, але з обмеженням з'єднань | природний: HTTP API, без з'єднань |

### Як масштабується запис при зростанні кількості датчиків

- **MySQL (одна інстанція).** Запис масштабується вертикально: більший клас інстанції, більше IOPS. Кожен паралельний обробник займає з'єднання, а їх кількість обмежена (див. [DATA.md](DATA.md)). З ростом кількості датчиків доводиться підіймати клас бази, додавати RDS Proxy або шардувати: це складно й дорого.
- **DynamoDB.** Дані розподіляються за хешем `sensor_id` по партиціях, і кожна партиція масштабується окремо. Режим `PAY_PER_REQUEST` підлаштовується під навантаження без налаштування, з'єднань немає, а плата іде за кожен запис. Кількість датчиків (різних значень ключа розділу) можна збільшувати майже без обмежень. Один датчик обмежений пропускною здатністю партиції (≈ 1000 записів/с), що для частоти 20-100 мс (до 50 записів/с) з великим запасом.

### Висновок: що обрати для потоку телеметрії

Для **зберігання потоку телеметрії і запиту «історія датчика за час»** краще підходить **DynamoDB** (або інша база часових рядів): ключ `sensor_id` + `measured_at` точно відповідає основному шаблону доступу, запис масштабується горизонтально без керування з'єднаннями, а плата пропорційна використанню.

**MySQL** потрібен там, де є запити, яких немає в DynamoDB: агрегація по всіх датчиках, фільтри за довільними полями, виявлені аномалії, звіти. Тому в цій системі вони доповнюють одне одного: DynamoDB зберігає сирий потік і віддає історію датчика, MySQL — оброблені дані для аналітики. Якби потрібно було обрати лише одну базу під масштабований потік датчиків, обрав би DynamoDB, а аналітику винес би в окремий сховище (наприклад, вивантаження в S3 + Athena).
