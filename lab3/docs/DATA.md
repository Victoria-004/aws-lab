# Збереження і читання історії

## Схема таблиці

Усі вимірювання зберігаються в одній таблиці `measurements` (MySQL 8.4, RDS `db.t3.micro`, база `iot`). Таблиця створюється функціями автоматично (`CREATE TABLE IF NOT EXISTS` у `functions/common/db.py`).

| Стовпець | Тип | Призначення |
|---|---|---|
| `id` | `BIGINT AUTO_INCREMENT`, PK | внутрішній ключ |
| `message_id` | `CHAR(36)`, **UNIQUE** | ідентифікатор повідомлення, ключ ідемпотентності |
| `sensor_id` | `VARCHAR(64)` | датчик |
| `sensor_type` | `VARCHAR(16)` | `temperature`, `humidity`, `light`, `camera` |
| `value`, `unit` | `DOUBLE`, `VARCHAR(16)` | значення як надіслав датчик |
| `value_norm`, `unit_norm` | `DOUBLE`, `VARCHAR(16)` | нормалізоване значення (°C, %, lux) |
| `delta` | `DOUBLE`, NULL | відхилення від попереднього вимірювання датчика |
| `is_anomaly`, `anomaly_reason` | `TINYINT(1)`, `VARCHAR(64)` | ознака й причина аномалії (`out_of_range`, `spike`) |
| `lat`, `lon` | `DOUBLE` | координати датчика |
| `measured_at` | `DATETIME(3)` | час вимірювання, UTC, з точністю до мілісекунд |
| `received_at` | `DATETIME(3)` | час приймання сервером |
| `object_key` | `VARCHAR(255)`, NULL | ключ знімка в S3 (лише камера) |

Індекси: `PRIMARY KEY (id)`, `UNIQUE uq_message_id (message_id)`, **`idx_sensor_time (sensor_id, measured_at)`**.

### Індекс для запитів за датчиком і часом

Запит історії має вигляд `WHERE sensor_id = ? AND measured_at BETWEEN ? AND ? ORDER BY measured_at DESC LIMIT ?`. Складений індекс `(sensor_id, measured_at)` обслуговує його повністю: MySQL знаходить діапазон за першим стовпцем, читає його за другим у зворотному порядку і зупиняється на `LIMIT`, не сортуючи рядки окремо.

## Одна таблиця чи таблиця на кожен тип

Обрано **одну таблицю з полем `sensor_type`**.

| | Одна таблиця (вибрано) | Таблиця на тип |
|---|---|---|
| Схема | у всіх типів однакова: значення, одиниця, час, координати | можна мати власні стовпці для кожного типу |
| Запит історії | один запит і один індекс для будь-якого датчика | треба знати тип, щоб обрати таблицю |
| Додати новий тип | достатньо нового значення `sensor_type` і правил обробки | нова таблиця, міграція, зміна коду |
| Запити «по всіх» (статистика, аномалії) | один `GROUP BY` | `UNION` з усіх таблиць |
| Розмір індексів | один великий індекс | менші, але їх більше |
| Недолік | рідкісні специфічні стовпці (`object_key`) порожні для інших типів | дублювання коду й DDL |

Тут усі типи мають однакову форму, а відмінності (`object_key`) вкладаються в один необов'язковий стовпець, тож єдина таблиця простіша. Окремі таблиці мали б сенс, якби типи сильно відрізнялися за схемою (наприклад, багатоканальний датчик із десятками параметрів) або за обсягом.

## Запит історії

`GET /sensors/{sensor_id}/history` (потрібен заголовок `x-api-key`).

| Параметр | Опис | За замовчуванням |
|---|---|---|
| `from`, `to` | межі часу, ISO 8601 в UTC (включно) | `to` = зараз, `from` = `to` - 1 година |
| `limit` | максимум записів, 1-1000 | 100 |
| `source` | `sql` або `nosql` (див. [NOSQL.md](NOSQL.md)) | `sql` |

Відповідь: масив у **зворотному хронологічному порядку** (найновіші першими). Помилки параметрів дають `400` з описом.

## Як функція підключається до бази

- База стоїть у **приватній підмережі** VPC, `publicly_accessible = false`, група безпеки пускає порт 3306 лише від групи безпеки функцій.
- Функції `processor` і `history` розгорнуті в тих самих приватних підмережах (`vpc_config`), тому звертаються до бази за її внутрішньою адресою.
- Параметри підключення (хост, користувач, пароль, ім'я бази) передаються змінними середовища, які задає Terraform. Пароль генерується (`random_password`) і не потрапляє в репозиторій.
- Драйвер — `pymysql` (чистий Python, лежить у архіві функції). З'єднання шифрується TLS.
- Об'єкт з'єднання створюється **один раз на екземпляр функції** (змінна рівня модуля) і використовується повторно в наступних викликах. На початку кожного виклику він перевіряється через `ping(reconnect=True)`.
- Доступ до DynamoDB і S3 з приватної мережі йде через безкоштовні gateway endpoints, тож NAT і вихід в інтернет не потрібні.

## Чому кількість з'єднань до бази є обмеженням для serverless-функцій

Реляційна база тримає кожне з'єднання як окремий потік зі своєю пам'яттю, а загальна кількість обмежена (`max_connections`, для `db.t3.micro` приблизно 60-85). Постійний застосунок має кілька процесів і невеликий пул з'єднань, тож тримається в межах ліміту. Lambda ж масштабується **кількістю одночасних екземплярів**, і кожен екземпляр відкриває власне з'єднання:

- при піку в 500 одночасних виконань було б 500 з'єднань, а база дозволяє кілька десятків: нові з'єднання відхиляються (`Too many connections`), функції падають, повідомлення повертаються в чергу;
- екземпляри створюються й зникають, а з'єднання, які вони не закрили, ще якийсь час висять у базі;
- холодний старт додає час на встановлення з'єднання і TLS-рукостискання.

Як це обмежено в цій системі:

1. `maximum_concurrency = 5` у тригері SQS: обробник не запускає більше 5 екземплярів, тож не більше 5 з'єднань.
2. Повторне використання з'єднання між викликами екземпляра.
3. Функція `history` викликається вручну і рідко, її з'єднань небагато.
4. Таймаут підключення 10 с і повторна спроба через механізм повторів SQS замість лавини з'єднань.

Інші рішення для більшого масштабу: **RDS Proxy** (пул з'єднань між функціями і базою), Aurora Serverless v2 з Data API (запити через HTTP без з'єднань), обмеження `reserved concurrency`, або перенесення часових рядів у DynamoDB, де з'єднань немає взагалі ([NOSQL.md](NOSQL.md)). RDS Proxy тут не використано, бо він платний і для навантаження емулятора не потрібен.
