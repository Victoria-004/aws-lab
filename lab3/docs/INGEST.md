# Приймання даних у чергу

Приймач — мінімальна Lambda-функція `ingest` за HTTP API (Amazon API Gateway). Вона перевіряє ключ, валідує поля і кладе повідомлення в чергу SQS `iot-lab3-measurements`, нічого не обробляючи. Усе описано в Terraform (`terraform/apigw.tf`, `lambda.tf`, `sqs.tf`).

## Запит

`POST <api_url>/ingest`, заголовки `content-type: application/json` і `x-api-key: <ключ>`.

| Поле | Тип | Правила |
|---|---|---|
| `sensor_id` | рядок | 1-64 символи: літери, цифри, `_`, `.`, `-` |
| `sensor_type` | рядок | одне з: `temperature`, `humidity`, `light`, `camera` |
| `value` | число | скінченне число (не рядок, не `NaN`, не булеве) |
| `unit` | рядок | непорожній, до 16 символів (`C`, `F`, `K`, `%`, `lux`, `klx`, `bytes`) |
| `location` | об'єкт | `lat` у -90..90, `lon` у -180..180 |
| `measured_at` | рядок | ISO 8601 **в UTC**: зона `Z` або `+00:00` обов'язкова |
| `object_key` | рядок | **лише для `camera`**, обов'язково: ключ знімка вигляду `camera/<sensor_id>/...` |

Тіло обмежене 16 КБ.

## Приклад

```bash
curl -i -X POST "$API_URL/ingest" \
  -H "x-api-key: $API_KEY" \
  -H "content-type: application/json" \
  -d '{
    "sensor_id": "temp-01",
    "sensor_type": "temperature",
    "value": 21.4,
    "unit": "C",
    "location": {"lat": 49.8397, "lon": 24.0297},
    "measured_at": "2026-11-21T18:00:00.123Z"
  }'
```

Відповідь `202 Accepted`:

```json
{"message_id": "0b0a6c0e-5a5b-4a39-9a7f-3d4f0c2e8f11"}
```

`message_id` видає приймач; за ним повідомлення відстежується далі в журналах обробника, і саме він є ключем ідемпотентності в базі.

Повідомлення в черзі додатково містить `received_at` — час приймання сервером (UTC).

## Помилки

`400 Bad Request` — опис помилок по полях:

```json
{
  "error": "validation failed",
  "details": [
    {"field": "value", "message": "required finite number"},
    {"field": "measured_at", "message": "must be in UTC"}
  ]
}
```

| Код | Причина |
|---|---|
| `202` | Повідомлення прийнято в чергу |
| `400` | Некоректний JSON або поля не пройшли валідацію (перелік у `details`) |
| `401` | Немає заголовка `x-api-key` або ключ невірний |
| `429` | Перевищено ліміт API Gateway (300 запитів/с, сплеск 600) |

## Чому приймач не обробляє дані, а лише складає їх у чергу

1. **Швидка відповідь і стійкість до піків.** Датчики не повинні чекати на базу. Приймач відповідає за кілька мілісекунд, а черга витримує сплеск навантаження: повідомлення чекають, поки обробник їх прочитає.
2. **Розділення відповідальності.** Приймач відповідає лише за автентифікацію і валідацію формату, обробник — за бізнес-логіку й збереження. Їх можна змінювати, масштабувати і налагоджувати незалежно.
3. **Збереження даних при збоях.** Якщо база недоступна або обробник зламаний, вимірювання не втрачаються: вони залишаються в черзі (до 4 діб) і будуть оброблені пізніше. Якби приймач писав у базу напряму, кожен збій бази означав би втрату або помилку 500 для датчика.
4. **Захист бази.** Обробник читає чергу з обмеженою паралельністю (до 5 екземплярів), тому кількість одночасних з'єднань до бази не залежить від навантаження на приймач ([DATA.md](DATA.md)).
5. **Повторна обробка.** Невдалі повідомлення повторюються і, зрештою, потрапляють у чергу недоставлених ([DLQ.md](DLQ.md)) замість того, щоб загубитися.
