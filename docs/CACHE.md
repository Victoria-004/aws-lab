# Кешування

## Схема

Операція `GET /districts` (список районів) переведена на cache-aside (`app/my_project/utils/cache.py`):

1. Сервіс шукає список у Redis.
2. Якщо він є — повертає його.
3. Якщо немає — читає з бази, зберігає в Redis на 45 с і повертає.

Redis запущений окремим ECS-сервісом у приватній мережі (`terraform/redis.tf`) і спільний для всіх задач застосунку. Кеш вмикається змінною `cache_enabled` у Terraform.

## Результати

Два прогони сценарію з [LOADTEST.md](LOADTEST.md), 8 листопада 2026. Файли: `docs/loadtest_nocache_*.csv` і `docs/loadtest_cache_*.csv`.

| Показник | Без кешу | З кешем |
|---|---|---|
| Латентність p95 | 11 с | 15 с |
| Запитів за секунду | 4,6 | 3,8 |
| Запитів до бази за списком районів | 798 | 23 |
| CPU бази | ≈ 6% | ≈ 5% |

**Частка влучань у кеш: 96,7%** (675 влучань, 23 промахи).

Кеш прибрав 97% запитів до бази за списком, і медіана `GET /districts` зменшилась з 1,8 с до 0,08 с. Загальна латентність не покращилась, бо вузьким місцем була не база (її CPU ≈ 5–6%), а процесор задачі застосунку (до 100%, поки працювала одна задача).

## Актуальність даних

Після запису клієнт може бачити старий список **до 45 секунд** — поки не сплине термін дії запису в кеші.

Як зменшити цей час:
- зменшити TTL (але тоді буде більше звернень до бази);
- видаляти список із кешу після кожного запису (змінна `cache_invalidate`).
